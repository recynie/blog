# Post 定位

Post 用于记录和分享技术工作的理解、实践与发现。围绕值得分享的核心思路展开，让读者理解为什么关注它、它如何解决问题，以及能从中得到什么。

内容以项目与软件介绍、模型架构解读、个人项目分享等技术主题为主。文章保持简洁、直接、重点明确，深度来自清晰的解释和判断。

# 撰写思路

- 读者意识：先明确这篇文章最值得分享的内容，以及希望读者获得的理解；据此取舍材料、设计主题。
- 拟定正文逻辑：设计整体叙事逻辑，让正文各个章节有逻辑衔接关系，这种衔接体现在章节内容，而不是章节之间的衔接语句。按内容需要展开，无须逐项覆盖或套用固定结构。
- 优先解释关键设计及其理由。例如：
  - 介绍或推荐项目时，可以讲清其定位、实现方式、使用场景、与类似产品的差异、局限；
  - 分享个人工作时，可以讲问题、数据处理、实验方法、实验结果等；
  - 分享论文或架构时，可以从背景问题、动机、方法、和相关工作的比较等。
- 让读者易于理解：正文要保证读者理解思想、跟随思路，正确性和严谨性在其次，将重要内容放到正文，补充说明放到footnortes、折叠块等内容，降低读者的认知负担。补充说明不作为正文叙述的一部分，读者不看补充说明也不影响理解文章的主要思路。典型的补充说明包括：防御性、严谨性相关的说明（结论具有局限性，方法可能不通用，数据可能有偏，等等），对概括性内容的补充（正文提及“有相关工作”，补充说明具体的几个相关工作）。
- 自包含：post最好是自包含的。新的概念或术语应当先定义后再使用，建议仅在能简化行文使新定义术语或概念。
- 行文风格：全文以直接的陈述性语言为主，减少无意义对比、曲折句式的使用。
- 技术细节以帮助理解为准。保留影响核心思路或结论的必要细节，省略具体实验参数、操作步骤和复现指南，避免写成实验报告或过程流水账。
- 鼓励询问问题，以增加对文章定位、主题的理解。不虚构作者经历、实验结果等事实内容，可以询问用户问题，让post的思路更连贯、更丰富。

# markdown语法使用方式

*标题*用于帮助读者了解章节内容，便于概览、跳转阅读，标题应当满足的条件：
- 清晰，读者不需要了解正文内容就能看懂标题
- 陈述性，客观陈述或概括章节的主要内容
- 名词性，对于陈述性的内容，建议用名词作为标题；对于互动性内容，可以灵活拟定

*footnotes*用于补充正文内容：
- 补充内容：一个内容有价值、但对理解post主线帮助较小，即便删除也不影响理解正文，作为补充或扩展提供给读者。
- 术语解释：对于一个读者可能不了解的术语的解释，可以简要解释，并附上质量较好的blog或wiki。
- 补充事实来源：例如项目主页、blog主页、论文。如果正文直接提及来源，那么用超链接即可。

*折叠内容块*用于：
- 补充大量的、相对重要的具体内容，例如重要的提示词等。

*引用块*用于重要且相对简短的补充内容，即便删除它也不影响理解正文：
- 总结、思路概括，一般是核心思路类的语句。谨慎使用，仅在必要时使用，仅在重复或总结正文思路时使用。
- 补充说明，例如说明总体方法的局限性等。这里指的是重要的说明，不重要的说明放到footnotes中。

# 工作方式

先理解用户意图和已有材料，再确定文章主线。
- 辅助撰写时保留用户想表达的重点；
- 独立起草时依据可靠资料形成主线，对影响文章方向的缺失信息与用户确认；
- 根据用户要求修改post时，避免将修订过程、修订历史、说明等加入post内容。post的读者是fresh context的，这类说明对读者来说是冗余信息，应当仅报告给用户。你需要保证修改后的post逻辑仍然连贯、读者能够很好理解、没有对读者冗余的信息。

完成后可以使用subagents检查：核心内容是否突出，思路是否连贯，是否存在删去也不影响理解的内容。
